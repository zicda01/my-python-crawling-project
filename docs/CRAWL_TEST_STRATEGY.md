# 단일 파일 크롤링 테스트 코드 개발 전략

## 간단한 정리

**고정된 나스닥 갤러리 PC 목록 첫 페이지의 HTML을 한 번 확보·저장하고, 이후에는 그 샘플을 읽어 게시글 정보를 추출한다.** 파서 검증 후 입력을 실제 HTTP 응답으로 바꿔 연결한다. 요청과 파싱은 한 Python 파일 안의 별도 함수로 나누며, 사용자 URL 입력·PC/모바일 선택·상세 본문 방문은 이후 단계로 옮긴다.

- 구현 파일: `crawl_test.py` 하나. capture·sample·live 모드를 구현했다.
- 실행: 추가 옵션 없이 `python crawl_test.py`.
- 기본 주소: `https://gall.dcinside.com/mgallery/board/lists/?id=nasdaq&page=1`.
- 핵심 기술: Python, requests, BeautifulSoup, 표준 urllib.parse·json·datetime·pathlib.
- 결과: 글 번호·제목·상세 URL·말머리·목록 작성일·조회수·추천수.
- 제외: 광고·설문·공지, 본문·댓글·작성자 정보, 페이지 넘김·DB·예약·AWS 배포.
- 샘플: `samples/nasdaq_list.html`과 응답 메타데이터. 한 번 확보한 샘플로 반복 파싱한다.
- 검증: 추출 결과를 샘플의 행과 대조하고, 마지막에 새 응답에서도 동작하는지 확인한다.

작성일: 2026-10-04. 전체 학습 단계는 [프로젝트 기획서](PROJECT_PLAN.md)를 따른다.

코드 구현 전에 [가상환경·Docker 전략](ENVIRONMENT_STRATEGY.md)에 따라 로컬 `.venv`와 의존성을 준비한다. 로컬과 Docker는 같은 코드·의존성 목록을 사용하며 `.venv` 자체는 배포하지 않는다.

## 1. 검토 결과와 이번 결정

기존 URL 입력 전략은 URL 정규화, 형식 선택, 두 종류의 상세 파서를 함께 다루므로 첫 실험의 범위가 컸다. 이번에는 갤러리 목록 한 페이지로 줄인다. 반복되는 게시글 행을 읽으면서 요청·파싱·자료 구조·저장을 순서대로 경험할 수 있다.

PC 목록은 앞선 검토에서 글 번호·제목·작성일·조회수·추천수와 페이지 구조를 확인했다. 이는 requests 코드의 성공이나 선택자 검증을 의미하지 않으며 실제 응답은 구현 때 확인한다. 모바일이 더 유리한지는 아직 검증하지 않았다. 첫 코드는 PC만 사용하고 자동 대안 요청은 넣지 않는다.

전체 V1 목표인 본문·DB·AWS 자동화는 유지한다. 이번 테스트는 V1의 첫 실험이며 전체 수집기의 완료 기준과 구분한다.

## 2. 학습 목표

완료 후 다음 내용을 설명할 수 있어야 한다.

- requests는 HTML을 받아오고 BeautifulSoup은 받은 HTML에서 데이터를 찾는다는 차이.
- 반복되는 게시글 행에서 필요한 열과 링크만 읽는 방법.
- 광고·설문·공지를 데이터에서 제외하는 기준.
- 상대 URL을 절대 URL로 만드는 방법.
- 원문 문자열과 정리한 정수·시각의 차이.
- HTTP 200이어도 차단 화면이나 다른 페이지라면 수집 성공이 아닌 이유.

## 3. 실행과 고정 설정

실행 예정 명령:

```bash
python crawl_test.py
```

코드 상단에 다음 상수를 둔다.

```python
BASE_URL = "https://gall.dcinside.com/mgallery/board/lists/?id=nasdaq&page=1"
TIMEOUT_SECONDS = 15
OUTPUT_DIR = "output"
SAMPLE_PATH = "samples/nasdaq_list.html"
RUN_MODE = "sample"  # capture / sample / live
```

15초는 초기 테스트값이다. 자동 재시도, URL 입력 프롬프트, CLI 옵션, 페이지 형식 자동 판별을 구현하지 않는다. 대상 URL은 사용자가 수정할 수 있는 명확한 상수로 두고 여러 곳에 반복 작성하지 않는다.

실행 모드는 코드 상단 상수로 지정한다. 매번 CLI 옵션이나 URL을 입력하지 않는다.

| 모드 | 입력과 처리 | 웹 요청 |
| --- | --- | --- |
| `capture` | HTML과 메타데이터 확보·저장. 내용과 구조를 먼저 관찰 | 목록 한 번 |
| `sample` | 저장된 HTML을 읽어 파싱·출력·JSON 저장 | 없음 |
| `live` | 새 HTML을 받아 같은 파서로 파싱·출력·JSON 저장 | 목록 한 번 |

개발 순서는 capture → sample 반복 검증 → live 대조다. 기본은 sample로 두고 샘플이 없으면 확보 절차를 안내하며 종료한다. 샘플이 없다고 자동 웹 요청하지 않는다. 새로 확보할 때 기존 샘플은 시각을 붙여 보존해 덮어쓰기 손실을 피한다.

첫 테스트에서는 예상 밖 리다이렉트를 별도 오류로 기록하고 다른 주소를 자동 방문하지 않는다. SSL 인증 검증을 유지한다. 합성 HTML과 실제 응답 샘플은 파일·메타데이터에 출처를 구분한다.

### 샘플 저장 규칙

- requests로 받은 응답에서 인코딩을 확인한 후 HTML 문자열을 UTF-8로 저장한다. 메타데이터에 응답 인코딩과 저장 인코딩을 각각 기록한다.
- `samples/nasdaq_list.meta.json`에 요청·최종 URL, 확보 시각(UTC), HTTP 상태, Content-Type, 인코딩을 기록한다.
- 오류 응답·차단 HTML은 정상 샘플과 구분해 진단용으로 보존할 수 있다. HTTP 200이나 파일 저장 성공만으로 정상 샘플이라 판단하지 않는다.
- 정상 샘플에는 실제 목록 영역과 게시글 행이 있는지 확인한다. 인코딩이 깨졌으면 파싱에 앞서 해결한다.
- HTML 확보 시각과 로컬 파싱 시각을 구분한다. 같은 샘플을 다시 읽은 시각을 데이터가 새로 수집된 시각으로 표시하지 않는다.
- live 모드에서는 HTML을 메모리에서 파싱하고 기본적으로 파일로 저장하지 않는다. 향후 운영 HTML 보관은 디버깅·재현 요구에 따라 별도로 결정한다.

## 4. 수집 필드와 행 처리

| 필드 | 처리 방식 |
| --- | --- |
| `post_id` | 실제 게시글의 양의 정수 번호 |
| `title` | 제목 링크에서 추출. 옆의 댓글 수나 아이콘 설명을 제목에 섞지 않음 |
| `url` | urljoin으로 상세 URL 생성. 나스닥 게시글인지 및 글 번호 일치 확인 |
| `category` | 말머리 문자열. 없으면 null |
| `published_at_raw` | 목록에 표시된 날짜·시간 문자열 그대로 보관 |
| `views` | 조회수 정수. 누락·변환 실패 시 null과 경고 |
| `recommendations` | 추천수 정수. 누락·변환 실패 시 null과 경고 |

목록의 시간만 보고 전체 작성 일시를 추측하지 않는다. 상세 페이지에 있는 정확한 작성 시각은 본문 수집 단계에서 보완한다.

행 처리 순서:

1. 갤러리 목록 영역과 게시글 행을 찾는다. 페이지 전체 링크를 순회하지 않는다.
2. 광고·설문·공지 여부를 먼저 확인하고 제외한다. 공지도 숫자 글 번호가 있을 수 있으므로 번호만으로 판별하지 않는다.
3. 글 번호·제목·상세 URL 등 필수 정보를 확인한다.
4. 나머지 선택 필드를 추출하고 변환한다.
5. 같은 글 번호가 중복되면 한 번만 포함하고 중복 건수를 기록한다.

일반 게시글로 보이는 행에서 필수 필드를 얻지 못하면 경고와 파싱 오류 행 수를 남긴다. 정상 제외 행과 파싱 실패 행을 구분한다. 모든 행이 실패했으면 정상적인 0건 수집으로 저장하지 않는다.

## 5. 단일 파일 함수 구성

| 함수 | 역할 |
| --- | --- |
| `fetch_html(url)` | 타임아웃·응답 상태·HTML 응답 여부 확인 |
| `save_sample(html, metadata)` | 확보한 HTML·응답 메타데이터 저장 |
| `load_sample()` | UTF-8 HTML과 확보 시각·출처 읽기 |
| `parse_list(html, base_url)` | 목록 영역 찾기, 행 제외·추출, 통계·경고 생성 |
| `save_result(result)` | UTF-8 JSON 저장 |
| `main()` | 모드에 따른 입력 → 공통 파싱 → 출력·저장, 오류 시 실패 종료 |

코드는 함수 중심으로 작성하고 클래스·복잡한 설정 계층을 추가하지 않는다. BeautifulSoup 파서는 Python 기본 `html.parser`를 사용한다. 선택자는 실제 응답에서 확인한 후 코드에 넣으며 구조를 추측해 확정하지 않는다.

`parse_list(html, base_url)`는 문자열만 받아 네트워크 요청과 파일 접근을 하지 않는다. sample과 live의 차이는 HTML을 얻는 부분이며, 필터링·필드 추출·결과 저장 로직은 재사용한다. 코드 파일은 하나로 유지하고 HTML·메타데이터·JSON은 데이터 파일로 분리한다.

터미널에는 응답 상태, 수집 건수, 제외·오류 건수, 제목 목록, 경고와 저장 경로를 표시한다. HTTP·파싱·저장 오류를 구분하고 실패 시 종료 코드는 0 이외로 반환한다.

## 6. JSON 출력

성공 결과는 실행 시각을 포함한 `output/nasdaq_list_<실행시각>.json`에 저장한다. 경로는 스크립트 위치 기준으로 잡아 실행 디렉터리가 달라도 결과 위치가 일정하도록 한다. 결과 파일·합성 HTML은 Python 소스 파일 하나와 별개다.

예시 (게시글 값은 합성 데이터):

```json
{
  "site": "dcinside",
  "gallery_id": "nasdaq",
  "source_url": "https://gall.dcinside.com/mgallery/board/lists/?id=nasdaq&page=1",
  "page": 1,
  "view": "pc",
  "source_mode": "sample",
  "collected_at": "2026-10-04T06:00:00Z",
  "parsed_at": "2026-10-04T06:05:00Z",
  "count": 1,
  "excluded_count": 2,
  "parse_error_count": 0,
  "warnings": [],
  "posts": [
    {
      "post_id": 123456,
      "title": "합성 예제 제목",
      "url": "https://gall.dcinside.com/mgallery/board/view/?id=nasdaq&no=123456",
      "category": "일반",
      "published_at_raw": "15:00",
      "views": 10,
      "recommendations": 0
    }
  ]
}
```

일부 행 실패가 있으면 정상 추출 데이터는 보존하되 경고와 오류 건수를 기록해 완전한 성공과 구분한다. 목록 자체를 찾지 못한 결과를 빈 성공 JSON으로 저장하지 않는다. 명시적인 빈 목록 화면이 확인되는 경우에만 정상 0건으로 처리한다.

## 7. 테스트와 완료 기준

| 테스트 | 확인할 결과 |
| --- | --- |
| 일반 행이 있는 예제 HTML | 번호·제목·URL·선택 필드 추출 |
| 샘플 읽기·반복 파싱 | 웹 요청 없이 같은 입력으로 같은 게시글 결과, 확보 시각 유지 |
| 샘플·메타데이터 누락 | 안내 후 실패 종료, 자동 실사이트 요청 없음 |
| 광고·설문·숫자 번호가 있는 공지 | 제외 기준에 따라 제거 |
| 제목 옆 댓글 수·아이콘, 상대 URL | 순수 제목과 올바른 절대 URL |
| 조회수·추천수 누락 또는 잘못된 값 | null과 경고. 0으로 임의 변환하지 않음 |
| 중복 글·일부 깨진 행 | 중복 제거, 오류 건수·경고 기록 |
| 목록 없는 HTML·차단 화면·HTTP 오류·타임아웃 | 성공으로 오인하지 않고 실패 반환 |
| JSON 저장과 읽기 | 한글 보존, count와 posts 길이 일치 |
| 허용 범위의 실제 목록 한 페이지 | 화면의 일반 글 몇 개와 번호·제목·링크 직접 대조 |

완료 기준은 **추가 입력 없이 목록 한 페이지의 실제 게시글 정보를 읽고, 필터링과 오류를 구분하며, 결과를 출력·JSON 저장하는 것**이다. 화면의 표시 행 수는 광고·공지가 포함되므로 성공 건수와 단순 비교하지 않는다. 모바일 지원이나 본문 추출이 없어도 이번 테스트는 완료할 수 있다.

확보한 샘플의 일반 글 몇 개를 수동으로 골라 글 번호·제목·링크·선택 필드를 대조한다. 동일 샘플의 반복 결과는 게시글 데이터 기준으로 비교하고, 실행 시각 차이는 허용한다. 새 페이지에는 글이 추가될 수 있으므로 live 결과와 이전 샘플의 글 목록이 같아야 한다고 판단하지 않는다.

### 구체적인 구현 순서

1. Python 실행 환경과 requests·beautifulsoup4 설치 상태 확인.
2. `fetch_html`과 `save_sample`을 구현해 한 번의 응답과 메타데이터 확보.
3. 샘플에서 목록·일반 행·광고·설문·공지·제목 링크의 실제 구조 확인.
4. 관찰한 선택자와 제외 규칙으로 `parse_list` 구현.
5. sample 모드에서 출력·JSON 저장, 제외·중복·오류 처리 검증.
6. live 모드에 같은 파서를 연결하고 새 응답을 대조.

2026-10-04 실제 HTML을 한 번 확보하고 선택자를 확인했다. 해당 샘플은 일반 글 45개, 제외 행 9개, 파싱 오류 0개로 처리됐다. 자동 검증 8개는 합성 HTML·임시 파일·모의 HTTP 응답으로 수행한다. 현재 결과는 이 샘플과 테스트 사례에 한정되며 이후 사이트 구조 변경에 대한 보장을 뜻하지 않는다.

확인한 선택자는 `table.gall_list`, `tbody > tr.ub-content`, `td.gall_num`, `td.gall_subject`, `td.gall_tit`, `td.gall_date`, `td.gall_count`, `td.gall_recommend`다. 공지는 `data-type="icon_notice"`, 광고·설문은 말머리와 아이콘으로 제외한다. 제목의 댓글 수 링크는 `.reply_numbox`로 구분한다.

명시적인 빈 목록 화면은 아직 관찰하지 않았으므로 0건 결과는 정상 성공으로 처리하지 않고 확인을 요청한다. capture는 응답을 저장한 뒤 목록 확인을 위해 파서를 실행하지만 결과 JSON은 저장하지 않는다. sample·live에서만 추출 JSON을 저장한다.

## 8. 후속 확장 순서

1. 목록에서 얻은 상세 URL 하나를 방문해 제목·본문·정확한 작성 시각 추출.
2. 소량의 여러 글을 순차 방문하고 요청 간 대기 적용.
3. SQLite 저장·중복 방지·배치 복구.
4. 전체 기획의 UI·Docker 검증·AWS 수동 배포·예약 실행.
5. 게시글 V1 완료 후 댓글 V2 확장.

URL 외부 입력과 모바일 비교는 필요가 생겼을 때 추가한다. 도입 시에는 갤러리 ID와 글 번호를 공통 식별자로 사용하고 요청·저장은 공통 코드, 파싱만 페이지 형식별로 분리한다. 네트워크 실패나 차단을 이유로 PC·모바일을 무조건 순차 요청하지 않는다.

## 9. 검토상 한계

- 첫 페이지에는 실행 시점의 일부 글만 있다. 전체 수집이나 누락 없는 수집을 보장하지 않는다.
- 이 단계의 조회수·추천수는 목록을 읽은 시점의 값이며 이후 변화는 추적하지 않는다.
- requests 응답에 필요한 HTML이 실제로 포함되는지는 구현 시 확인한다.
- Python 코드와 검증을 구현했다. Docker 이미지·AWS 자원은 만들지 않았다.
- 실사이트 요청은 [전체 기획서의 수집 정책 검토](PROJECT_PLAN.md)를 따른다. 로컬 합성 HTML로도 파싱·저장 테스트를 먼저 진행할 수 있다.
