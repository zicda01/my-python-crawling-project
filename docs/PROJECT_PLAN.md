# 주식 커뮤니티 데이터 수집 프로젝트 기획서

- 작성일: 2026-10-04
- 상태: 초기 기획. 크롤러 구현 및 실제 배치 운영 전.
- 검토 상태: 학습 목표에 맞춰 EC2 중심의 기본안을 정리함. AWS 자원은 생성하지 않음.
- 첫 대상: 디시인사이드 나스닥 마이너 갤러리 (`nasdaq`)

## 1. 목적

국내외 주식 커뮤니티의 데이터를 수집하고 DB에 정리한다. 첫 대상으로 나스닥 갤러리를 선택한다. **V1은 게시글만으로 수집·저장·Docker 실행·AWS 예약 실행·UI 확인을 완성하고, V2에서 댓글 수집과 갱신을 추가한다.** 댓글은 최종 목표에 유지하되 V1의 완료 조건에는 포함하지 않는다.

이 프로젝트는 학습 목적을 함께 가진다. 처음부터 복잡한 도구를 도입하지 않고 교과서적인 HTTP 요청, HTML 파싱, 관계형 DB 저장 방식으로 시작한다. 몇 차례 작은 테스트를 진행한 후, 관찰한 문제와 필요에 근거해 기술을 발전시킨다.

사용자는 Docker를 이미 활용할 수 있으므로 초기부터 Docker를 실행 환경으로 사용한다. 클라우드는 AWS를 기준으로 하고, AWS 서비스의 역할과 배포·운영 흐름을 배우는 것도 프로젝트 목표에 포함한다. 수집 작업은 예약 시간에 시작해 처리 후 종료하며, 로컬 컴퓨터가 꺼져 있어도 자동 수행되는 것을 목표로 한다.

### 핵심 학습 목표와 우선순위

1. **Python 데이터 크롤링 학습:** V1에서 HTTP 요청, HTML 파싱, 페이지 탐색, 데이터 정제, SQL 저장, 중복 방지, 예외 처리와 복구를 직접 구현한다. V2에서 댓글의 추가 로딩과 변경 데이터 처리를 학습한다.
2. **Docker 기반 작업의 스케줄링 및 클라우드 배포 학습:** 이미지 빌드, 환경 설정, 볼륨과 영속 저장, 일회성 컨테이너 실행, 예약 호출, 클라우드 배포를 익힌다. Docker는 실행 환경을 제공하고 예약 시점은 별도의 스케줄러가 관리한다.
3. **기본적인 AWS 서버 학습:** 서버 접속, 네트워크와 보안 그룹, IAM, 저장소, 로그, 인스턴스 시작·종료 등 기본 운영 원리를 이해한다.

학습 목표에 비추어 **EC2에서 Docker를 직접 실행하는 경로를 기본안으로 제안**한다. Linux 서버 접속과 운영을 직접 경험할 수 있기 때문이다. 앞서 제안한 ECS/Fargate는 첫 버전 구현 범위에서 제외하고 후속 비교 학습 대상으로 둔다.

서버 학습과 예약 시에만 컴퓨팅을 사용하는 요구를 단계적으로 충족한다. 먼저 EC2를 수동으로 시작해 수집 컨테이너를 실행·검증한다. 이후 AWS 외부 스케줄러로 EC2 시작을 요청하고, 부팅 후 일회성 수집 작업을 실행하며, 결과 저장 후 인스턴스를 중지하는 구성을 검토한다. 부팅 지연, 재부팅 시 중복 실행, 실패 시 종료, 최대 실행 시간, 중지 후에도 유지되는 저장소를 검증해야 한다. EC2 내부의 cron만으로는 중지된 EC2를 시작할 수 없다.

EC2 중지는 삭제와 구분하며 저장 공간 등의 비용은 별도로 확인한다. 기능 확장은 세 학습 목표를 달성하는 데 필요한 범위부터 진행한다. 아래 기술 구성은 구현을 위한 제안이며 인스턴스 종류·실행 시간·운영 비용은 AWS 배포 전에 결정한다.

## 2. 사용자 요구사항

1. 사용자가 특정 게시글 번호를 시작점으로 설정한다.
2. 시작 번호부터 이후 게시글을 수집한다.
3. 매일 한 번, 사용자가 지정한 시간에 배치를 자동 실행한다.
4. 이전 실행 이후의 새 글을 중복 없이 저장한다.
5. V1에서는 게시글을 저장하고 V2에서 게시글과 댓글을 연결해 저장한다.
6. UI에서 수집 설정, 저장된 게시글, 실행 결과를 확인한다. 댓글 표시는 V2에서 추가한다.
7. 수집용 EC2는 예약 실행 시 시작하고 작업 종료 후 중지한다.

‘특정 게시글부터’는 현재 **지정한 글 번호 이상을 수집하고 이후 새 글을 계속 추가하는 방식**으로 해석한다. 과거 방향으로 내려가는 수집이 필요하다면 범위 설정을 추가한다.

## 3. 초기 검토 결과와 미확인 사항

나스닥 갤러리 목록에는 글 번호, 말머리, 제목, 작성일, 조회수, 추천수가 있고 페이지 이동이 가능하다. 상세 페이지에서는 제목, 본문, 정확한 작성 시각을 확인했다.

댓글은 V2 시작 시 추가 검증한다. 검토한 상세 페이지에서 표시된 댓글 수와 웹 도구가 추출한 댓글 영역의 수가 달랐다. 따라서 초기 HTML만으로 전체 댓글을 얻을 수 있는지, 별도 로딩이 필요한지, 댓글 ID와 답글 관계를 어떻게 얻을 수 있는지는 V2 시작 시 확인한다. 댓글 수가 표시된다는 사실만으로 수집에 성공했다고 판단하지 않는다.

검토한 목록에는 주식 외 일상 글도 있었다. 첫 버전은 특정 종목이나 주식 관련 글을 자동 분류하지 않고, 지정 범위의 일반 게시글을 저장한다. 광고와 설문은 제외하며 공지는 기본 제외하는 방안을 제안한다.

### 수집 관련 정책

2026-10-04 검토 기준, 디시인사이드 이용약관 제16조는 사전 서면 동의 없는 크롤링을 명시적으로 금지한다. robots.txt의 일반 봇 허용 규칙만으로 이 프로젝트의 수집이 허용된다고 판단하지 않는다. 기술적 구현 가능성과 서비스의 허용 여부를 구분하며, 실제 자동 수집 전 허용 여부를 확인한다.

정책 확인 중에도 합성 예제 HTML과 데이터를 이용해 파싱, DB 저장, 배치, UI를 개발하고 검증할 수 있다. 차단 우회, CAPTCHA 우회, IP 교체를 통한 제한 회피는 초기 구현 범위에 포함하지 않는다.

## 4. 버전별 범위

V1 포함:

- 나스닥 갤러리 한 곳 수집
- 시작 글 번호 및 배치 실행 시간 설정
- 제목, 본문 텍스트, 말머리, 작성 시각, 원문 URL 저장
- 조회수, 추천수, 수집 시각 저장
- 중복 방지, 제한된 재시도, 실행 로그
- 저장 데이터와 배치 결과를 확인하는 간단한 UI

V2 포함:

- 댓글과 답글 수집, 게시글 연결
- 원본 댓글 ID 기반 중복 방지 및 내용 갱신
- 최근 게시글 재방문과 댓글 수집 상태 관리
- UI에 댓글과 갱신 시각 표시

후속 단계:

- 다른 국내외 커뮤니티 추가
- 종목 추출, 주식 관련 글 분류, 감성 분석
- 이미지·영상 다운로드 및 OCR
- 대규모 과거 데이터 수집
- 다중 작업자, 대규모 운영

초기에는 작성자 닉네임, 계정 ID, 일부 IP를 수집하지 않는 안을 제안한다. 목적 달성에 필요한지 확인한 뒤 수집 항목을 결정한다. 본문에 포함된 개인정보와 원문 보관·삭제 기준도 운영 전에 정한다.

## 5. 기본 기술 구성

| 역할 | 초기 선택 | 학습할 내용 |
| --- | --- | --- |
| 구현 언어 | Python | 함수 분리, 예외 처리, 모듈 구성 |
| 페이지 요청 | requests | HTTP 응답, 세션, 타임아웃 |
| HTML 파싱 | BeautifulSoup | 목록·본문 영역 선택, 텍스트 정리 |
| DB | SQLite + 표준 sqlite3 | 테이블, 고유 제약, 트랜잭션, UPSERT |
| 수동 배치 | Python CLI | 설정 입력, 반복 처리, 실행 기록 |
| UI | Streamlit | 설정 화면, 검색, 상세 조회 |
| 실행 환경 | Docker | 로컬과 클라우드에서 동일한 이미지 실행 |
| 이미지 저장 | Amazon ECR | 이미지 빌드·업로드·버전 관리 |
| 클라우드 서버 | Amazon EC2의 Linux 인스턴스 | 서버 접속, Docker 설치, 서버 시작·중지 |
| 영속 저장 | Amazon EBS + Docker bind mount | SQLite·작업 상태를 컨테이너 외부에 저장 |
| 예약 실행 | Amazon EventBridge Scheduler | 한국 시간 하루 한 번 EC2 시작 API 호출 |
| 부팅 후 실행 | systemd 일회성 서비스 + 실행 스크립트 | Docker 준비 후 수집, 결과 보관, 서버 종료 |
| 결과·백업 | Amazon S3 | SQLite 스냅샷과 실행 결과 보관, 로컬 UI 조회 |
| 로그 | 파일 로그, 이후 Amazon CloudWatch Logs | 실행 로그 및 실패 원인 확인 |
| 접근 권한 | AWS IAM 역할 | 스케줄러·실행 환경·프로그램 권한 구분 |

먼저 `requests`로 페이지를 받고 `BeautifulSoup`으로 필요한 영역을 읽는 순차 수집기를 만든다. 댓글이 동적으로 로딩된다면 로딩 방식을 확인하고, 허용 범위의 요청으로 얻을 수 있는지 검증한다. 그래도 기본 방식으로 목적을 달성할 수 없을 때 Playwright 등 브라우저 자동화를 검토한다.

처음부터 Docker를 사용하되, 비동기 요청, 분산 큐, 프록시, ORM은 필수로 도입하지 않는다. 실제 테스트 결과가 도입 이유를 제공할 때 추가한다.

### AWS 실행 구조와 학습 순서

```text
Docker 이미지 → ECR에 저장
EventBridge Scheduler → EC2 시작
    → systemd 실행 스크립트 → Docker 수집기 일회 실행
    → EBS의 SQLite에 데이터·진행 위치 저장
    → 일관된 DB 스냅샷·실행 결과를 S3에 보관 → EC2 중지
로컬 Streamlit UI → S3의 마지막 완료 스냅샷 다운로드 → 읽기 전용 조회
```

Docker는 실행 환경, EventBridge Scheduler는 예약 시점, systemd는 서버 부팅 후 작업 실행을 담당한다. 첫 버전은 EC2 한 대와 순차 수집기 하나로 운영한다. launchd는 로컬 예약 실험이 필요할 때만 선택적으로 사용한다.

로컬에서는 Docker와 SQLite 볼륨으로 기본 수집·저장을 학습한다. 이후 이미지를 ECR에 올려 EC2에서 수동 실행하고, 정상 동작을 확인한 뒤 부팅 자동 실행과 예약 시작을 연결한다. Mac에서 빌드할 때는 이미지와 EC2의 CPU 아키텍처를 일치시킨다. 배포 이미지는 버전 태그 또는 digest로 고정한다.

SQLite는 EBS의 호스트 디렉터리를 컨테이너에 마운트해 저장한다. 컨테이너 내부 파일시스템에만 저장하지 않는다. EC2 중지 후에도 EBS 데이터는 유지되지만 인스턴스 삭제 시 보존 여부는 별도로 설정해야 한다. RDS와 PostgreSQL은 초기 필수 구성에서 제외한다.

S3에는 SQLite backup API 등으로 만든 일관된 스냅샷을 업로드한다. 쓰기 중인 DB 파일을 단순 복사하지 않으며, WAL 모드에서는 DB 본체만 복사하는 방식에 특히 주의한다. S3 객체를 SQLite의 실시간 DB 파일로 마운트하지 않는다. EBS DB가 원본이고 UI용 스냅샷은 읽기 전용이다. 복원 절차를 소량 데이터로 검증한다.

‘예약 실행 때만 활성화’는 EC2 컴퓨팅을 대상으로 한다. 중지 중에도 EBS·S3·이미지·로그 등 보관 비용은 남을 수 있다. 수집 완료 후 OS 종료가 인스턴스의 **중지**로 이어지도록 shutdown behavior를 확인한다.

UI는 단계적으로 제공한다. V1에서는 로컬 Streamlit으로 마지막 완료 스냅샷의 게시글·실행 기록을 조회하고 마지막 실행 시각과 스냅샷 생성 시각을 표시한다. 댓글은 V2에서 추가한다. 실시간 실행 중 화면은 제공하지 않는다. EC2가 중지되어 있어도 마지막 저장 결과를 확인할 수 있다.

최종 UI에서는 AWS SDK인 boto3를 통해 예약 시간 변경과 수동 실행을 연결한다. 수집 설정은 버전이 있는 S3 설정 파일에 저장하고 배치가 시작 시 읽는다. 예약 시간은 EventBridge Scheduler가 실제 실행의 기준이며 DB settings는 적용된 설정의 기록으로 사용한다. 설정 저장과 예약 변경이 모두 성공했을 때만 적용 완료로 표시하고 부분 실패를 노출한다. 초기 개발 단계에서는 CLI·AWS 콘솔로 설정하고 UI 제어 기능은 뒤에 구현한다. 웹 UI 상시 배포는 후속 단계다.

장기 AWS 접근 키를 이미지에 넣지 않는다. 로컬 UI는 개발자 AWS 인증을, EC2는 IAM 인스턴스 역할을 사용한다. 설정 업로드·예약 변경·수동 시작 권한은 조회 권한과 구분한다.

스케줄러의 EC2 시작 성공과 수집 프로그램의 작업 완료를 구분한다. 실행 기록과 종료 결과를 확인해 수집 실패를 판단하며, 스케줄러 재시도만으로 수집 실패가 자동 복구된다고 가정하지 않는다. EC2 한 대의 프로세스 잠금과 DB의 실행 기록으로 수동·예약 작업의 중복을 막는다.

user data는 최초 설치용으로 사용하고 매 부팅 작업은 systemd로 등록한다. user data가 기본적으로 매번 실행된다고 가정하지 않는다. 부팅 시 예약 활성화·한국 날짜·해당 일자의 완료 상태를 확인하고, 명시적인 수동 실행 요청이 있을 때만 같은 날짜의 추가 실행을 허용한다. 개발·관리 목적 부팅 시 자동 수집을 끌 수 있게 한다.

최대 실행 시간을 두고 정상 완료·실패·시간 초과 모두에서 실행 기록과 로그를 보존한 후 중지를 시도한다. 부팅 실패 등에 대비한 외부 마감 중지 스케줄도 배치 시간대 이후에 둔다. 마감 중지는 작업을 끊을 수 있으므로 짧은 트랜잭션과 다음 실행 복구를 검증한다. 업로드 실패 시 EBS 원본을 유지하고 로컬 UI에 오래된 스냅샷임을 표시한다. 실시간 알림은 후속 개선 대상으로 둔다.

AWS 학습 단계에는 VPC·서브넷·보안 그룹, 서버 관리 접속, 외부 사이트 접속 경로, IAM 역할, EBS·S3, 로그 보관 기간을 포함한다. SQLite를 네트워크 DB로 노출하지 않는다. 초기에는 단일 서버 구조로 시작하고 네트워크 구성과 비용은 배포 전에 확인한다.

## 6. 배치 처리 흐름

### 단일 파일 목록 테스트 전략

첫 실험은 **고정 PC 목록 HTML 한 번 확보·저장 → 샘플 구조 관찰 → 로컬 반복 파싱·JSON 저장 → 새 HTTP 응답에 같은 파서 연결**이다. URL 입력이나 PC·모바일 옵션 없이 실행하고, 한 Python 파일 안에서 요청·파일 읽기·파싱을 함수로 분리한다.

- 기본 주소: `https://gall.dcinside.com/mgallery/board/lists/?id=nasdaq&page=1`.
- 수집 필드: 글 번호·제목·상세 URL·말머리·목록 작성일 원문·조회수·추천수.
- 광고·설문·공지 제외. 본문·댓글·페이지 넘김·DB·예약은 이 실험에서 제외.
- 공지는 숫자 번호가 있을 수 있어 번호만으로 필터링하지 않는다.
- 목록 HTML 구조를 실제 응답에서 확인하고 실패를 빈 결과와 구분한다.
- 학습용 HTML·응답 메타데이터를 samples에 저장한다. 확보 시각과 로컬 파싱 시각을 구분하며 운영 모드에서는 기본적으로 HTML을 저장하지 않는다.
- 후속 실험에서 목록의 상세 URL 하나를 방문해 본문을 추출한다.
- URL 외부 입력·모바일 비교는 이후 필요에 따라 도입한다. 모바일 우위는 미검증 상태다.

함수 구성·출력·테스트·완료 기준은 별도 [테스트 코드 개발 전략](CRAWL_TEST_STRATEGY.md)을 따른다. 첫 목록 실험의 완료와 게시글 V1 전체 완료는 구분한다.

V1은 게시글만 처리한다. V2에서 댓글 수집과 최근 글 재확인을 추가한다.

```text
설정 읽기 → 중복 실행 잠금 → 실행 기록 생성
    → 목록에서 이번 수집 상한과 대상 글 발견
    → 대상 작업 등록 → 본문 수집 → DB 저장
    → 이전 실패 건 재시도
    → 진행 위치 및 실행 결과 기록 → 잠금 해제
```

### 범위와 진행 위치

- 최초 실행은 설정한 시작 글 번호 이상을 대상으로 한다.
- 배치 시작 시 목록에서 확인한 최신 글 번호를 이번 실행의 상한으로 고정한다.
- 목록 페이지를 탐색해 실제 존재하는 글 번호를 찾는다. 번호를 하나씩 증가시키며 상세 URL을 방문하지 않는다.
- 이후 실행은 이전 발견 범위 이후의 새 글을 찾되, 경계 페이지를 겹쳐 확인해 목록 이동에 따른 누락을 줄인다.
- 글 번호가 없는 구간을 실패 또는 삭제로 단정하지 않는다.
- 첫 시작 번호를 너무 오래된 글로 지정하면 초기 작업이 커질 수 있으므로, 개발 테스트에는 최대 글 수·페이지 수 제한을 둔다.
- 최초 범위 수집은 테스트의 최대 100개 제한과 구분한다. 제한에 도달했으면 미완료 범위와 탐색 위치를 남기고 다음 실행에서 이어가며, 첫 범위 탐색 완료 전 최신 번호까지 처리한 것으로 표시하지 않는다.
- 진행 위치는 DB 저장 이후 갱신한다. 목록 탐색이 불완전한 실행은 범위를 완료로 처리하지 않는다.

### 중복 방지와 복구

게시글은 `(site, gallery_id, source_post_id)`에 고유 제약을 둔다. 재수집 시 UPSERT로 기존 행을 갱신한다.

발견한 글마다 작업 상태를 저장한다. 중간에 실패한 글은 별도로 남겨 다음 실행에서 다시 처리한다. ‘가장 큰 글 번호’만 기록해서 중간 실패를 놓치지 않도록 한다.

V1에서는 본문 수집 상태를 관리한다. V2에서는 게시글 저장과 댓글 수집 상태를 구분한다. 본문 저장에 성공하고 댓글만 실패했다면 게시글은 유지하고 댓글 수집을 재시도한다. 실행 중단 후에도 완료한 글부터 다시 저장할 필요 없이 남은 작업을 이어갈 수 있게 한다.

### V1 게시글 변경 정책

- 최초 수집한 본문·조회수·추천수를 보관하며 기존 글의 수정·삭제를 추적하는 정기 재방문은 하지 않는다.
- 재수집 시 UPSERT로 동일 행을 갱신할 수 있지만 정기 갱신을 보장하지 않는다.
- UI에 수집 시각을 표시해 최초 수집 결과임을 드러낸다.

### V2 댓글과 변경 내용 — 초기 정책안

- 새 글 수집 시 댓글도 수집한다.
- 최근 3일 글의 댓글·조회수·추천수를 다시 확인하는 설정을 제안한다. 기간은 변경 가능하게 한다.
- 원본 댓글 ID로 중복을 방지하고, 제공되는 경우 부모 댓글 ID로 답글 관계를 저장한다.
- 댓글 페이지가 여러 개면 전체 페이지를 확인하고 실제 저장 건수를 검증한다.
- 원본 댓글 ID를 얻을 수 없는 경우 대체 식별 방식의 충돌·수정 문제를 검토한 뒤 정한다.
- 최근 글 재확인 기간 이후에 추가된 댓글은 초기 정책으로 놓칠 수 있다. 전체 재수집이 필요한지는 테스트 후 결정한다.
- 네트워크 오류와 삭제를 구분한다. 한 번 접근에 실패했다고 글이나 댓글을 삭제 처리하지 않는다.
- 초기에는 최신 내용을 보관하고 수정 이력 전체 보관은 후속 검토한다.

최근 3일 재확인은 V2의 테스트용 제안값이며 확정 요구가 아니다. 댓글 추가 시점과 요청량을 관찰한 뒤 기간을 결정한다. V2 시작 시 기존 게시글 전체를 소급 수집하지 않고 신규 글과 선택한 최근 범위부터 적용한다.

### 요청과 실행 제어

- 요청은 순차 처리하고 요청 간 대기 시간을 설정한다.
- 타임아웃과 최대 재시도 횟수를 둔다.
- 일시적 오류에는 대기 시간을 늘려 재시도한다.
- 403, 429 또는 차단 안내가 나오면 무한 재시도하지 않고 중단·대기 상태를 기록한다.
- 예약 실행과 UI 수동 실행에 같은 잠금을 적용한다.
- 배치는 일회 실행 명령으로 만들고 스케줄러가 호출한다. UI를 열어 두어야만 예약 작업이 실행되는 구조는 피한다.

## 8. UI 초안

### 수집 설정

- 갤러리 및 시작 글 번호
- 매일 실행 시간(KST), 예약 활성화 여부
- 최근 글 댓글 재확인 기간 (V2)
- 지금 실행 및 현재 실행 상태
- 설정 변경 결과와 다음 실행 예정 시각

조회 UI를 먼저 만들고 설정 변경·수동 실행을 후속 개발 단계에서 연결한다. ‘지금 실행’은 EC2 시작 요청만으로 완료 처리하지 않는다. 중지된 서버는 수동 실행 요청을 기록하고 시작하며, 이미 실행 중인 서버에는 초기 버전에서 중복 요청을 거절하고 상태를 표시한다. 요청 접수와 배치 완료를 별도로 표시한다.

시작 번호는 최초 수집에 사용하며 이후 실행은 DB의 진행 위치를 따른다. 시작 번호 변경만으로 기존 데이터를 삭제하거나 진행 위치를 초기화하지 않는다. 과거 범위 재수집은 별도 기능으로 확장한다.

### 게시글 목록과 상세

- 날짜, 키워드, 말머리 검색
- 제목, 작성 시각, 수집 당시 조회수·추천수 표시
- 본문과 원문 링크 확인; 댓글과 답글은 V2에서 추가
- 마지막 수집 시각과 본문 수집 상태 확인; 댓글 상태·갱신 시각은 V2에서 추가

### 실행 이력

- 실행별 시작·종료 시각 및 처리 범위
- 신규·갱신·실패 건수
- 실패 이유, 재시도 상태
- 수집 결과가 실제로 0건인지 오류로 0건인지 구분

## 9. 단계별 학습·개발 계획

각 단계는 **학습 → 작은 구현 → 정상·실패 테스트 → 결과 기록** 순서로 진행한다. Docker는 처음부터 사용하고 3단계에서 영속 저장과 재현성을 집중 검증한다. 이전 단계 완료 기준을 충족한 뒤 다음 단계로 넘어간다.

| 단계 | 학습 내용·산출물 | 완료 기준 |
| --- | --- | --- |
| 1. Python 목록·본문 파싱 | HTTP 상태·인코딩·타임아웃, HTML 선택자, 페이지 탐색, 텍스트 정제. 산출물: 고정 PC 목록 정보 출력 후 상세 게시글 하나로 확장하는 코드 | ID·제목·본문·시각 대조, 광고 제외, 빈 본문과 오류 구분 |
| 2. SQL 저장·증분 배치 | SQLite, 고유 제약, UPSERT, 트랜잭션, 진행 위치, 재시도. 산출물: 시작 번호로 실행하는 게시글 배치 | 동일 범위 재실행에 중복 없음, 중간 실패·중단 후 복구, 제한 도달 시 미완료 범위 보존 |
| 3. Docker 실행 검증 | 이미지·컨테이너, 의존성 고정, 환경 변수, bind mount, 종료 코드. 산출물: Dockerfile·실행 예시 | 새 컨테이너에서 같은 결과, 컨테이너 제거 후 DB 유지, 실패 종료 코드·로그 보존 |
| 4. 조회 UI | Streamlit, SQL 검색, 수집 시각과 실행 상태 표시. 산출물: 게시글·실행 이력 화면 | 날짜·키워드 검색, 본문·원문 비교, 0건 성공과 실패 구분 |
| 5. AWS 서버 수동 운영 | EC2·Linux 접속, VPC·보안 그룹, IAM, ECR, EBS, S3. 산출물: 배포·중지·복원 절차 | 같은 이미지로 AWS 수집 실행, EC2 중지·시작 후 DB 유지, S3 스냅샷을 로컬 UI에서 조회·복원 |
| 6. AWS 예약 자동화 | Scheduler와 systemd, 부팅 의존성, 중복 방지, 시간 초과·종료 처리. 산출물: 예약·서비스 설정 | 최소 세 회차에 정상·실패·중단 후 복구 확인, Mac이 꺼져 있어도 실행, 작업 후 EC2 중지 |
| 7. UI 제어·V1 완성 | boto3, 설정 버전, 예약 변경, 수동 실행, 부분 실패 처리. 산출물: 설정·실행 제어 화면 | 설정이 다음 배치에 적용, 중복 요청 거절, 요청 접수와 완료 구분, V1 완료 기준 충족 |
| 8. 댓글 수집·DB 확장 (V2) | 댓글 로딩·페이지 탐색·원본 ID·답글 관계, 스키마 마이그레이션. 산출물: 댓글 모듈·테이블·조회 화면 | 기존 게시글 유지, 댓글·답글 연결, 댓글 없음과 실패 구분, 댓글 중복 없음 |
| 9. 댓글 갱신 (V2) | 최근 글 재방문, 수정·누락 처리, 본문·댓글 독립 재시도, 요청량 측정. 산출물: 갱신 배치·정책 기록 | 댓글 추가·내용 변경 반영, 일시 누락을 삭제로 오인하지 않음, 재확인 범위·실행 시간 검증 |

### 단계별 설명할 수 있어야 하는 내용

- 1~2단계: requests와 BeautifulSoup의 역할 차이, 최대 글 번호만 저장하면 누락되는 이유, 고유 제약과 트랜잭션의 목적.
- 3~4단계: 컨테이너 종료와 DB 삭제가 다른 이유, 설정과 이미지를 분리하는 이유, UI와 수집기를 독립적으로 실행하는 이유.
- 5단계: EC2·EBS·S3·ECR의 역할, 중지와 삭제의 차이, IAM과 보안 그룹의 차이.
- 6~7단계: Docker가 예약을 담당하지 않는 이유, 중지된 EC2 안의 cron으로 서버를 켤 수 없는 이유, 서버 시작 성공과 배치 완료의 차이.
- 8~9단계: 새 글만 수집하면 늦은 댓글을 놓치는 이유, 댓글 실패와 게시글 저장을 분리하는 이유, 갱신 기간과 요청량의 관계.

### 테스트와 학습 기록

각 단계에 실행 명령, 입력 범위, 예상·실제 결과, 발견한 문제, 수정 이유를 기록한다. 작은 입력부터 시작해 최대 100개 테스트로 확대한다. 성공뿐 아니라 타임아웃·실패·중복·중단을 확인한다. 테스트 크기 제한은 운영 수집 범위 완료와 구분한다.

파서는 합성 HTML, DB는 임시 SQLite로 검증한다. 실사이트 검증은 허용 여부 확인 후 소량 수행하며 반복 검증이 불필요한 요청을 늘리지 않도록 한다. 응답 → 추출 → 저장 결과를 직접 대조한다.

V1 자동화가 완료되기 전에는 댓글 기술, Playwright, PostgreSQL 등으로 범위를 넓히지 않는다. V2에서도 기본 요청·파싱의 한계를 확인한 뒤 필요한 기술만 추가한다.

## 10. 기술 발전 기준

| 관찰한 문제 | 검토할 개선 |
| --- | --- |
| 기본 요청으로 필요한 공개 댓글을 읽을 수 없음 | 로딩 방식 검증 후 브라우저 자동화 도입 여부 결정 |
| 데이터량·검색 시간이 증가함 | 인덱스 개선, PostgreSQL 전환 |
| UI와 배치의 DB 접근 충돌 | 짧은 트랜잭션, SQLite 설정 조정, 필요 시 DB 전환 |
| AWS 예약 호출 또는 수집 작업이 실패함 | 시작 실패와 작업 실패를 구분한 재시도·알림 정책 |
| 여러 커뮤니티를 추가함 | 공통 데이터 모델과 사이트별 수집 모듈 분리 |
| 처리 시간이 하루 배치에 맞지 않음 | 요청량·재확인 정책 최적화 후 제한된 동시 처리 검토 |

클라우드 운영에서는 예약 시각, 지연 허용 범위, 중복 호출, 실패 및 보충 실행 정책을 스케줄러 검증 단계에서 정한다.

## 11. 버전별 완료 기준

V1에서는 사용자가 UI에서 시작 글 번호와 매일 실행 시간을 설정하고, 해당 범위의 제목·본문을 DB에 저장할 수 있다. 여러 번 실행해도 중복이 생기지 않고 실패한 작업이 남아 복구된다. UI에서 원문과 저장 결과를 대조하고 실행별 성공·실패를 확인할 수 있다.

예약 실행은 최소 세 회차 관찰한다. 정상 완료, 의도한 수집 실패, 실행 중단 후 복구를 검증하고 EC2가 계속 켜져 남지 않는지 확인한다. 서버 중지 중에도 마지막 완료 스냅샷을 로컬 UI에서 조회할 수 있다. AWS 시작 요청 성공만으로 프로젝트 완료라고 판단하지 않는다.

V2 완료 기준은 기존 V1 데이터를 유지하면서 댓글·답글을 연결하고, 추가·수정·일시 누락·댓글만 실패하는 사례를 구분하는 것이다. 재확인 기간과 요청량을 테스트 결과로 결정하고 UI에 댓글 갱신 시각을 표시한다.

첫 구현은 **Docker 환경에서 고정 PC 목록 한 페이지 요청·파싱·JSON 저장**으로 시작한다. 이후 상세 본문 하나, 소량 여러 글, SQLite 저장 순으로 확장한다. 게시글 배치 복구를 검증한 뒤 UI와 AWS 수동·예약 실행을 연결한다. V1 완료 후 댓글을 추가한다.
